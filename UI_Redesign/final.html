Note it
One ring, not two
The grab indicator currently draws an outer and an inner ring. Two concentric rings read as a target reticle — “aim here” — which is the wrong verb for a thing you reach out and take. One ring that expands and breathes when the hand enters range says “within reach” without borrowing anything from aiming. It also halves the overdraw on a translucent element.

When does the token expand?

You asked what happens after an Explain step finishes. I read AdvanceProgress rather than guessing, and the answer is cleaner than I expected: the code already distinguishes the two cases for you.

Explain finishes mid-procedure → a row ticks. Nothing else. No Next.
OnExplainCompleted fires, the Game Manager calls AdvanceProgress(), and that does PageProgressMemory[CurrentViewingIndex]++ (TrainingStepPage.cpp:466) — it ticks one sub-step row, refreshes the list, plays a sound and scrolls. AdvanceProgress never turns the page. There is nothing for the trainee to press, so expanding the board would interrupt them for no reason. The token just updates its count — 2/5 becomes 3/5 — and widens to the alert state for about two seconds so the change is noticed in the periphery.
Token stays
Explain finishes the last sub-step → the procedure completes. Now expand.
Same call, but CurrentProgress >= TotalSubSteps (TrainingStepPage.cpp:476) so it also does MaxUnlockedIndex++, fires OnMasterStepCompleted, writes progress to UChapterSubsystem, and calls UpdateNextButtonState() — which is the moment Next stops being dead. That is the only point in a procedure where the trainee has something to press, so that is the only point the token should open to the full board.
Token expands
So the rule is one line, and it needs no new state
Expand on OnMasterStepCompleted. Pulse on everything else. Both are already broadcast; the token does not have to count anything itself or know what kind of interaction just finished — Explain, Action, Grab, Latch and Touch all funnel through the same AdvanceProgress.
Free
Quizzes are the exception, and the code already guards it
AdvanceProgress returns immediately if the current step is a Quiz (TrainingStepPage.cpp:445-448) — “Quizzes are strictly advanced by the user clicking Confirm.” A quiz page therefore has to open by itself, because nothing will ever tick it forward. That is the one place the board should expand unasked.
Auto-open
One behaviour to know about before it surprises a trainee
If the trainee has paged back to read an earlier procedure and a sub-step then completes, AdvanceProgress silently jumps the view forward to MaxUnlockedIndex first (TrainingStepPage.cpp:450-461). With a big fixed board that is merely jarring; with a token that expands, the board opens on a different page than the one they were last reading. Worth a short cross-fade, or simply not expanding when CurrentViewingIndex != MaxUnlockedIndex.
Design in
And the scroll destination is wrong for a shorter board
ScrollToActiveSubStep uses EDescendantScrollDestination::IntoView (TrainingStepPage.cpp:505), which does the minimum scroll — parking the active row flush against the bottom edge. At 1.9 m everything fit so it never showed. Change it to Center.

Before anyone builds this

Seven things the source says that the design does not. Each one is cheap now and expensive later.

Your 900 × 870 design is currently rendering into a ~500 × 500 target
The designer's Width/Height is DesignTimeSize, inside #if WITH_EDITORONLY_DATA (UserWidget.h:1528-1532) — preview only. Your root is a Canvas Panel, and SConstraintCanvas::ComputeDesiredSize (SConstraintCanvas.cpp:356) returns the max of the children's slot offsets, not the canvas size. With bDrawAtDesiredSize on, CurrentDrawSize = SlateWindow->GetDesiredSize() (WidgetComponent.cpp:1432-1437). Set bDrawAtDesiredSize = false and DrawSize = (900, 870). Fix this first — every other quality decision is downstream of it.
Fix first
The dimmed-pending reveal needs a RichTextBlock, not the TextBlock you have
UTextBlock has exactly one ColorAndOpacity for the whole widget (TextBlock.h:37-40) — no per-range colour at all, and UMG exposes no HighlightText. Showing read text white and pending text at 26% in one paragraph means URichTextBlock plus a UDataTable of two FRichTextStyleRows differing only in colour (RichTextBlock.h:22-29,50-51). Today ExplainTextBlock is a plain UTextBlock, so the current reveal must be appending characters rather than dimming them. This is a real change, not a re-skin — and re-emitting the markup on every reveal tick re-runs the parser, so measure it.
Asset + C++
The audio scrubber needs BarFillStyle = Scale, or the rounded fill breaks
FProgressBarStyle carries independent BackgroundImage and FillImage brushes (SlateTypes.h:1180-1187), each with its own CornerRadii — so rounded track and rounded fill both work. But the default EProgressBarFillStyle::Mask draws the fill at full width and clips it (SProgressBar.cpp:462-467), which squares off the leading edge. Set UProgressBar::BarFillStyle = Scale (ProgressBar.h:44).
One field
I was wrong about the cable auto-select — the horizontal axis is not stable
All six components billboard with FindLookAtRotation (Azr_Explain.cpp:265 and five siblings). That returns zero roll, so UpVector stays near world-up and Top/Bottom is stable — but RightVector spins with the player, so a Left/Right auto-choice inverts every time the trainee crosses the widget–mesh line, and the cable head pops across the panel. So the v1 rule is Top/Bottom only: with the token docked at the bottom, anchor at Top and it can never cross. Left/Right auto-selection needs hysteresis and is not worth it yet.
Corrected
And the default is the exact edge the token sits on
FAzr_TetherConfig::WidgetAnchorPos = EAzr_TetherPos::Bottom (Azr_Types.h:150). Every authored asset that already set it keeps its value, so a new default only affects new content — existing steps need the field changed, or an Auto enumerator appended at the end of EAzr_TetherPos so serialized content does not renumber.
Per step
There are six copies of CalculateSurfaceAnchor, not four
Azr_Explain.cpp:1061, Azr_Action.cpp:610, Azr_Grab.cpp:1187, Azr_Latch.cpp:1266, Azr_Touch.cpp:508, Azr_AttachTarget.cpp:461 — the repo conventions doc says the tether block is copy-pasted across four files, and that is stale. All six are private and non-virtual across two different base classes, so there is no seam: any change is six edits unless a free helper is introduced first. Two of them differ — AttachTarget's takes no FAzr_TetherConfig, and Touch silently drops the Front/Back cases (Azr_Touch.cpp:525-531), so those anchor at the widget centre instead.
Six edits
Two small ones that bite silently
Tracking kills ligatures. Standard ligatures are enabled only when letter-spacing is exactly 0 (SlateTextShaper.cpp:735), and the offset quantises to an int16 pixel advance — so fine tracking at small sizes steps rather than scales. Rounded-box radii are not clamped. SlateShaderCommon.ush:69-120 applies the radius verbatim with no min(radius, size/2), so a pill segment narrower than twice its radius inverts and artifacts — clamp the minimum segment width in layout.
