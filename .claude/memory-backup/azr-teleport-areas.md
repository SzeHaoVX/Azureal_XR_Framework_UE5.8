**User's design (2026-07-28), chosen over navmesh tuning / surface-normal validation:** author walkable space directly with resizable boxes instead of relying on navmesh generation. Navmesh was "very troublesome" for **second floors** (bounds must enclose every level; thin platforms often don't generate) and **tight closets** (navmesh carves anything narrower than the agent radius, so the floor exists but the navmesh doesn't → reticle invalid even though the player fits).

**`AAzr_TeleportArea`** (`Azr_TeleportArea.h/.cpp`, AzurealXR runtime): an Actor whose root is a `UBoxComponent` named `Area`. Drop it in the level, resize over the floor the player may teleport onto. **Collision is `NoCollision` and overlaps are off** — containment is a pure point-in-box math test (`ContainsPoint`), so nothing is baked and the box can never block the teleport arc or hand scanners. Box is `ShapeColor` green, `bHiddenInGame=true`, `bDrawOnlyIfSelected=false` (always visible while authoring). `bStartEnabled` + `EnableArea()`/`DisableArea()`/`IsAreaEnabled()` let training steps gate rooms. `VerticalTolerance` (default 25) adds slack above/below so the box doesn't need exact floor alignment. Actors self-register into a `static TArray<TWeakObjectPtr>` Registry on BeginPlay / unregister on EndPlay (no `GetAllActorsOfClass` while aiming); statics `HasAnyArea(World)` / `IsPointInAnyArea(World, Point)` filter by world so PIE and editor worlds don't cross-talk. Math note: `InverseTransformPosition` divides out scale, so it compares against `GetUnscaledBoxExtent()` and converts the tolerance by `Scale.Z`.

**Two modes per area.** Default (`bUseAsLandingSurface=false`): the arc flies through the box (no collision), hits the real floor, and the box just answers "is that floor point inside me?" — so **the box must ENCLOSE the floor surface**; a box floating in mid-air validates nothing. With `bUseAsLandingSurface=true`: the arc is intersected against the box itself (`IntersectSegment`, `FMath::LineExtentBoxIntersection` in box-local space) and the player lands on the box's **top face**, with the beam trimmed at that point — for platforms/scaffolds with no floor collision or a standing plane in mid-air. `FindArcLanding` walks the arc polyline in order so the first surface wins, and runs BEFORE the world-hit path in `UpdateArc`. Debug fill: `bShowDebug` + `DebugFillOpacity` draw a navmesh-style translucent green solid (`DrawDebugSolidBox` + edge `DrawDebugBox`) via Tick, with `ShouldTickIfViewportsOnly()` returning `bShowDebug` so it renders in the editor viewport; grey when disabled; tick switched off at BeginPlay when debug is off.

**Why a box and not a plane:** the default mode tests where the arc hit the *floor*, and floors are never perfectly flat (steps, thresholds, ramps) — a plane would need a thickness tolerance anyway, which is exactly what the Z extent is. The Z extent also separates floors (a ground-level hit under a second-floor box is correctly rejected). To get a plane, just flatten Box Extent Z.

**`UAzr_Teleport` integration:** new `EAzr_TeleportValidation ValidationMode` (`Auto` default / `TeleportAreas` / `NavMesh`) + private `ValidateDestination(HitPoint, OutLocation)` which replaced the inline `ProjectPointToNavigation` block in `UpdateArc()`. **Auto = areas if the level has any enabled one, else navmesh** — so existing navmesh levels keep working untouched until the first `Azr_TeleportArea` is placed. With areas, the pawn lands **exactly where aimed** (no navmesh snapping); with navmesh it still uses `NavLoc.Location`. The arc itself is unchanged (`PredictProjectilePath` vs `WorldStatic`), so floors still need normal collision for the beam to land — only the *validation* stopped depending on navmesh.

**Gotcha found after shipping the areas: the PAWN had its own second navmesh gate.** `AAzr_Pawn::ProcessStickInput` hard-coded `ProjectPointToNavigation` for BOTH backward blink-step and backward smooth-move, so with the navmesh gone backward locomotion silently died even though teleport worked. Worse, the failed blink still ran `bReadyToSnapTurn = false`, and that lock is SHARED with snap turn — so every backward push swallowed the player's next snap turn (presented as "backwards and snap rotate don't work"). Fixed by: `UAzr_Teleport::IsDestinationValid(Location)` (public, BlueprintCallable; wraps `ValidateDestination` with a taller `(50,50,250)` nav probe — `ValidateDestination` now takes a `NavQueryExtent` param defaulting to `(50,50,50)` for the arc) + `AAzr_Pawn::IsBackwardDestinationAllowed()` which defers to the teleport component, falls back to navmesh if there is no teleport component, and returns **true** if the level has neither (so backward is never silently dead). The lock is now only consumed when the blink actually executes. **Lesson: locomotion validation lived in two places — check `Azr_Pawn.cpp` too, not just `Azr_Teleport.cpp`.**
